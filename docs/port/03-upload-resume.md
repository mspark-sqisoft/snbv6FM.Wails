### 1.3 Wails 판의 지금 상태(`E:\git\snBv6FM.Wails`)

`client.go`·`README.md` 를 읽은 결과다.

- 된 것: TLS 로그인(암호 모드 0만), 서버 파일 목록, **파일 하나 업로드**, 다운로드.
- 업로드(`client.go` `Upload`)가 하는 일:
  - 결재 방식: 업무망(`LOC=1`)이면 `fm_influp_aprv`, 아니면 `fm_otflup_aprv`. 6(자가)이면 결재자 = [자기 ID].
  - `fm_upfile_mode != "1"` 이고 결재 방식이 0이 아니면 막는다(결재자 선택이 없어서).
  - `resv` 는 결재자가 있으면 `"1"`, 없으면 `"2"`. 결재 방식 3이면 `aprv_kind=3`.
  - `fm_checksum != "0"` 이면 SHA-256 소문자 16진을 먼저 계산한다.
  - 512KB 청크로 보내고, 실패하면 `defer cancel` 로 스트림을 끊는다.
  - `Send` 가 EOF 를 주면 `Recv` 로 서버 사유를 꺼낸다. 끝나면 `CloseSend` 뒤 `Recv` 루프에서 `Res != 1` 이면 거부로 본다.
- 안 된 것(README 표): 결재자 고르기, 폴더 zip, 동시 전송·서랍·취소, 자동 업로드.

## 3. 서버 통신

### 3.1 RPC

```
service ServerFileService {
  rpc FileUpload(stream FileUploadRequest) returns (stream AnswerResponse);
}
message FileUploadRequest { oneof data { FileTransInfo info = 1; bytes chunk = 2; } }
message AnswerResponse { int32 res = 1; int32 code = 2; string reason = 3; int64 length = 4; string txt = 5; }
```

- 옛 전문 번호: **C-3320**(서버 `svc_fileupload.go` 의 `process_3320`, 응답 3021). 로그·서버 대조 때 이 번호로 찾는다.
- 양방향 스트림이다. 클라이언트가 먼저 `info` 하나를 보내고, 서버의 수락 응답 뒤 `chunk` 를 보낸다(원본은 수락 응답을 기다리지 않고 바로 청크를 보낸다 ― 3.3절).

### 3.3 순서(정상)

```
클라이언트                                   서버(svc_fileupload.go)
  ── info(FileTransInfo) ──────────────▶   첫 메시지가 info 인지 확인(아니면 오류)
                                             권한·크기 검사
  ◀───── res=1 code=0 "Allow file send" ─   (하루 한도가 있으면 code=5, reason=하루 누적)
  ── chunk(512KB) × N ─────────────────▶   Recv 루프, 파일에 쓴다
  ── CloseSend(끝 알림) ────────────────▶   EOF 를 받으면 크기를 보지 않고 커밋(SR002)
                                             postUploadCommit(DB 기록·암호화)
  ◀───── res=1 "Successfully uploaded file"
  (서버 핸들러 종료 → 스트림 상태 OK)
```

- 원본은 첫 응답 `"Allow file send"`(res 1, code 0)를 특별히 기다리지 않는다. 응답이 올 때마다 `res != 1` 이면 거부로 보고, 스트림이 끝난 뒤 `상태 OK && 보낸 양 == 파일 크기 && 거부 없음` 이면 성공이다.
- Wails 판(`client.go`)은 지금 끝에서 `Recv` 루프를 돌며 `Res != 1` 을 거부로 본다. 첫 응답 code 5(하루 한도 누적)는 무시해도 된다(원본도 읽지 않음).

### 3.6 결재 방식(`aprv_type`)을 정하는 곳과 원본 결함 의심

- 결재 방식 값: 0 자동, 1 사전, 3 사후, 4 요청 때 선택, 6 자가, 7 전체(`imports/FileMoverPolicy/README.md` `ENUM_APRV_TYPE`).
- 업로드 파일: 업무망(location==1)이면 `fm_influp_aprv`, 아니면 `fm_otflup_aprv`(`loginrespolicy.cpp` `getAprvType`). 클립보드는 `fm_inclup_aprv`/`fm_otclup_aprv`.
- 사후결재 갈래(`checkUpFileMode`, `upfileMode_ != 0`)는 각 파일에 `isAfter=true`, `aprvType = getAprvType(...)` 를 넣는다.
- **사전결재 갈래(`upfileMode_ == 0`)는 업로드 객체의 `aprvType` 을 넣는 곳이 없다.** `_T_FILE_TRANS_OBJECT` 생성자도 `aprvType` 을 초기화하지 않는다(`tcpDefine.h` 186-207). 근거: 원본 저장소를 `\.aprvType\s*=` 로 찾아 `ViewController.cpp:1013`(다운로드)·`1457`(클립보드)·`2302`(사후)만 나왔다. 그러므로 사전결재 업로드의 `aprv_type` 에 정해지지 않은 값이 갈 수 있다. 실제로 무엇이 가는지(대개 0일 것으로 추정)는 확인하지 못했다.
- Wails 판은 **늘 `getAprvType` 값을 넣는다**(지금 `client.go` 가 이미 그렇다). 서버가 `aprv_type` 을 어떻게 쓰는지에 따라 원본과 결과가 달라질 수 있으므로 9절에서 서버 `fm_approve` 행을 대조한다.

### 3.7 사전결재 갈래에서 업로드 전에 부르는 조회(06 영역과 공동)

- `getApproverList`(결재자 목록) + `setDeptInfo`(부서 정보 [3250]·[3252]) → 결재자 선택창.
- 조회가 실패하면 원본은 앱에 알림이 없어 업로드 목록이 풀리지 않는다(보류 067 "결재자 조회가 멈춤" ― 로그아웃 전까지 사람의 업로드가 거절됨). Wails 판은 조회 실패를 오류로 받아 목록을 놓는다.

### 5.1 서버 파일 화면의 업로드 입구(`content/ServerFileScrollView.qml`)

### 5.2 업로드 흐름(사람이 올릴 때)

```
[파일 업로드]/[폴더 업로드]/드롭
  → uploadFiles: 개수 초과? 로그인? 망 허용? 목록 주인 판정 → __CLIP__ 빼기
  → checkUploadFiles(작업 스레드): 파일마다 기준값(크기·수정 시각) 남기고 검사, 폴더는 스냅샷 + 검사
       └ [파일 검사 결과] 창(번호 gen)
  → fileCheckReply(gen, reject)
       ├ 취소·차단 있음 → 목록 놓기, 로그 `사용자에 의해 파일 업로드가 취소되었습니다.`
       └ 진행 → checkUpFileMode
              ├ 사전(0): 결재 방식 0/6 → 창 없이 / 그 밖 → [결재자 선택] 창 → setApproverAndCause
              │          → 폴더 압축(zipFoldersThen) → addTransFile(사유, 결재자)
              └ 사후(1): isAfter=true, aprvType → sendFiles(압축 → addTransFile)
  → addTransFile: 서랍 행 추가(`대기중`) → 대기열에 넣기 → 전송 시작(로그 `BATCH 전송 시작 >>> 대기 업로드[%1] 다운로드[%2]`)
```

### 5.3 업로드 목록 주인 규칙표(`src/UploadGate.h`)

| 지금 주인 | 들어온 요청 | 결과 | 로그·화면 |
|---|---|---|---|
| 없음 | 아무거나 | 받음(Take) | |
| 아무나 | 자동 업로드 | 건너뜀(SkipAuto) | `[Auto]자동 업로드 >>> 답을 기다리는 업로드가 있어 이번 주기를 건너뛴다` |
| 자동 | 사람 | 밀어냄(PreemptAuto): 세대 증가, 자동 업로드 검사 창 닫기 | `자동 업로드 검사를 멈추고 사람의 업로드를 받는다` |
| 사람 | 사람 | 거절(RejectHuman) | 알림 띠 `앞 업로드를 마친 뒤 다시 시도하세요.`, 로그 `업로드 거절 >>> 앞 업로드가 답을 기다리는 중이다` |

검사 창 답 판정(`judgeCheckReply(replyGen, currentGen, resultGen, isReject)`):
- 답의 번호 ≠ 지금 번호 → 버림. 로그 `파일검사 회신 >>> 지난 검사의 답이라 버린다 ...`
- 진행 답인데 그 번호의 결과가 아직 창에 나오지 않음 → 버림. 로그 `파일검사 회신 >>> 결과가 나오기 전의 답이라 버린다 ...`
- 나머지 → 받음.

### 5.4 [파일 검사 결과] 창(`content/FileCheckResultDlg.qml`)

- 열 때(`show(gen)`): 상태 초기화, `검사가 진행중입니다.`, [확인] 숨김.

  - 오류 0건: `검사결과 모두 정상 파일입니다.` + 2000ms 뒤 자동으로 진행 답.

## 7. 로컬 처리(알고리즘과 Go 패키지 후보)

### 7.1 패키지 구성(제안)

```
internal/transfer/   대기열(Queue), 전송 워커, 진행률 묶기, 정지 감시
internal/upload/     업로드 목록 주인(Gate), 검사 답 판정, 스냅샷·변경 판정, 폴더 압축
internal/autoupload/ 폴더 주기 감시, done 옮기기
app.go               Wails 서비스 메서드·이벤트(화면 입구)
client.go            gRPC 호출(기존 Upload 를 대기열 워커가 부르게 다듬음)
```

### 7.2 전송 대기열(원본 `TransferQueue` 그대로 + 고침)

```go
type State int // Unknown, Pending, Active, Done, Failed, Cancelled
type Dir int   // Upload, Download

type Item struct {
    ID    int64 // atomic 발급
    Dir   Dir
    Size  int64
    Key   string // 중복 판정: 정리한 절대 경로 + "|" + 크기 + "|" + 수정 시각(ns)
    State State
    Wait  string // 대기 사유
    cancel context.CancelFunc
}

type Queue struct {
    mu        sync.Mutex
    items     map[int64]*Item
    pending   [2][]int64     // 방향별 FIFO
    active    [2]int
    keys      map[string]int64 // Pending·Active 인 Key → ID (중복 금지)
    maxConc   int              // 5
    serialMin int64            // SERIAL_TRANSFER_SIZE × 1MB
    wake      chan struct{}
}
```

규칙(원본과 같은 것):
- `Enqueue`: 이미 아는 ID 면 거부(상태 무관). **추가**: 같은 Key 가 Pending·Active 이면 거부.
- `limit(dir)`: 그 방향의 Pending·Active 중 `Size > serialMin` 이 하나라도 있으면 1, 아니면 `maxConc`.
- `Next(dir)`: `active < limit` 이면 맨 앞을 Active 로 바꿔 돌려줌.
- `Complete(id, result)`: Active 일 때만 바꾸고 참. 참일 때만 다음을 출발시킴(두 번 불려도 안전).
- `Cancel(id)`: Pending 이면 빼고 Cancelled. Active 면 `cancel()` 을 부르고, 워커가 끝나며 `Complete(id, Cancelled)`.
- 상태는 Queue 한 곳에만 둔다. 화면은 Queue 가 내는 이벤트만 그린다(원본의 "대기열은 취소·화면은 실패" 불일치가 생기지 않는다).

`limitLocked` 를 "대기 중인 것까지 본다" 는 원본 규칙은 그대로 둔다 ― 작은 파일 5개 진행 중에 큰 파일이 대기열에 들어오면 그 뒤로 새 출발이 1개로 묶인다. 이 규칙이 메모리 상한(대용량 동시 금지)의 근거다.

### 7.3 업로드 워커(한 파일)

```
1. 상태 Active, 이벤트 progress(0, "전송 준비중...")
2. 검사값: fm_checksum 켜짐이면 preHash 에서 꺼내거나 계산(대기 사유 "대기중(검사값 계산)" 이 먼저 나감)
   계산 뒤 ctx.Err() 면 로그 `업로드 취소됨 - 체크섬 계산 중에 정리됐다` 로 끝냄
3. os.Open → 실패 -123
4. changedSinceCheck("보내기 전") → 다르면 -978
5. stream := FileUpload(ctx) → 실패 -972
6. 수신 고루틴: for { r, err := stream.Recv(); res!=1 → rejected=r.Code, cancel(); ... }
7. Send(info) → 512KB 씩 Read → Send(chunk). 진행 바이트 atomic 증가
8. 끝: changedSinceCheck("끝 알림 전") → 다르면 cancel + -978
9. CloseSend → 수신 고루틴 종료 대기
10. 판정: rejected 있으면 그 code / 끝 신호 전 오류 또는 sent!=size → -974 / 끝 신호 뒤 오류: 서버가 답한 실패면 -970, 답을 못 받으면(끊김·상한 초과) -9996 / 아니면 성공(100, `파일업로드 성공 >>> ...`)
```

- 지금 `client.go` `Upload` 를 이 구조로 옮긴다. 다른 점: 수신을 별도 고루틴으로 돌려 **거부를 받는 즉시** 보내기를 멈춘다(원본보다 낫게, 3.4절).
- 청크 버퍼는 워커마다 512KB 하나를 재사용한다. gRPC `Send` 는 메시지를 직렬화해 내보낸 뒤 돌아오므로 버퍼 재사용이 안전하다(grpc-go 의 `SendMsg` 문서: 반환 뒤 메시지를 고쳐도 된다).

### 7.4 검사값과 미리 계산

- `crypto/sha256` + `io.CopyBuffer`(1MB 버퍼). 결과 `hex.EncodeToString`(소문자).
- 미리 계산: 검사 창에서 진행이 나면(`fails==0`) 시작. 폴더(zip 뒤에야 알 수 있음)나 `serialMin` 보다 큰 파일이 섞이면 맨 앞 1개만, 아니면 `limit` 개까지 고루틴. 결과는 `map[ID]string` 에 두고 워커가 꺼낸다. 취소는 ctx.
- 원본은 해시를 위해 파일을 한 번 다 읽고, 보낼 때 또 읽는다(두 번). 첫 메시지(`info.checksum`)에 실어야 해서다. "보내며 계산해 마지막에 싣기" 는 서버 규격 변경이 필요해 보류.

### 7.5 스냅샷·변경 판정(`UploadSnapshot.h` 옮김)

- 파일 기준값: `{size, mtimeMs}`(원본 기본값 -1 = 기록 없음 → 대조하지 않음).
- 폴더 스냅샷: `filepath.WalkDir`, 숨김 제외, 키는 `/` 구분 상대 경로, 값은 `{size, mtimeMs}`.
- `diffSnapshots(before, after, ignore)` → added / removed / changed(이름순). 원본 로그 형식 그대로: `업로드 취소 >>> 검사 뒤 내용이 달라졌다 >>> 폴더: <경로> 더해짐 N [..] 없어짐 N [..] 바뀜 N [..]`.
- 숨김 판정: Windows 는 `golang.org/x/sys/windows` 의 `GetFileAttributes` & `FILE_ATTRIBUTE_HIDDEN`(Qt `QDir::Hidden` 이 Windows 에서 보는 것과 같게). macOS·Linux 는 이름이 `.` 으로 시작. 추정: Qt 는 Windows 에서 `.` 시작 이름을 숨김으로 보지 않는다 ― 시험으로 맞춘다.
- 수정 시각 비교는 ms 로 자른다(원본이 ms). NTFS 는 100ns 이지만 원본과 같은 해상도로 둔다.

### 7.6 배압과 메모리 상한(제약 "메모리 ≤ 파일 크기")

원본:
- 앱 큐 + Qt + 소켓에 아직 못 나간 양(`unflushedSendBytes`)이 `max(3MB, 보내는 업로드 수 × 2 × 512KB)` 를 넘으면 읽기를 멈춘다.
- 실측(원본 README·ADR-0004): 95MB 하나 +6MB, 다섯 동시 +45MB.

Go 판 설계:
- 워커는 `Read → Send` 를 차례로 한다. `Send` 는 HTTP/2 흐름 제어 창과 grpc-go 의 스트림 쓰기 몫이 차면 막힌다 → 워커당 메모리는 "청크 버퍼 512KB + 전송 계층 버퍼" 로 묶인다(추정: 스트림당 64KB 쓰기 몫, 연결 창 64KB~). **실측 필요**.
- 그러므로 따로 배압 코드를 쓰지 않는다(YAGNI). 실측에서 넘으면 `grpc.WithWriteBufferSize`·`WithInitialWindowSize` 로 묶는다.
- 청크를 2MB 넘게 키우지 않는다 ― 서버 수신 상한 4MB(암호화 모드에서 약 1.5배)에 걸릴 수 있다.
- 메모리 상한 판정: 5개 동시 전송 중 앱 RSS 증가 ≤ 각 파일 크기 합 이고 ≤ 50MB(원본 실측 +45MB 이하)를 목표로 9절에서 잰다.

### 7.7 정지 감시와 끊김 감지

- 워커마다 `lastProgress atomic.Int64`(UnixNano). 진행 바이트가 늘 때 갱신.
- 감시 고루틴 하나가 1초마다 Active 업로드를 돌며 `now - lastProgress > UPLOAD_STALL_SEC` 이면 그 워커의 결과를 -975 로 정하고 `cancel()`. 로그 `업로드 실패 - 서버 응답이 없어 전송을 중단했습니다(N초) >>> ...`.
- 원본은 "보낼 큐 크기가 변하지 않음" 을 보고, Go 판은 "Send 를 지난 바이트가 늘지 않음" 을 본다. `Send` 가 막혀 있으면 바이트가 늘지 않으므로 같은 뜻이다.
- 연결 자체의 끊김: 이미 keepalive Time 30s 를 건다(`client.go`). `Timeout` 도 20s 로 함께 걸어 반쯤 열린 연결을 감지한다(추정 값, 서버 keepalive 정책 `MinTime` 과 맞는지 확인 ― 너무 잦으면 서버가 `ENHANCE_YOUR_CALM` 으로 끊는다).
- 연결이 끊기면(`Unavailable`) 진행 중인 것은 -974(끝 신호 뒤면 -9996), 대기 중인 것은 한꺼번에 실패로 정리하고 01 세션 영역의 끊김 처리로 넘긴다.

### 7.8 이어올리기·이어받기(서버 규격이 생겼을 때의 설계 메모, 지금은 구현하지 않음)

- 업로드: `FileTransInfo` 에 `offset`(이어 보낼 위치)과 서버가 가진 부분 파일의 크기·해시를 물어볼 RPC 가 필요하다. 클라이언트는 `(경로, 크기, 수정 시각, 검사값)` 이 같을 때만 이어 보낸다.
- 다운로드: `FileDownloadRequest` 에 `offset` 이 필요하다. `.snbpart` 크기에서 이어 받고 끝에서 전체 검사값을 대조한다(지금 다운로드가 이미 `.snbpart` + 검사값 대조를 한다).
- 서버 요청은 SR006(회신 없음)에 이 칸 제안을 덧붙인다.

### 7.9 폴더 압축

```
tmpDir := os.MkdirTemp(<userData>/temp, "up-*")
zipPath := filepath.Join(tmpDir, folderName + ".zip")
w := zip.NewWriter(f)
WalkDir(folder): 숨김 건너뜀, 폴더는 건너뜀(원본처럼 파일만), excludes[절대경로] 건너뜀
  hdr := &zip.FileHeader{Name: 상대경로(슬래시), Method: zip.Deflate, Modified: mtime}
  io.Copy(w.CreateHeader(hdr), file)
압축 직전·직후 스냅샷 대조 → 다르면 tmpDir 통째 삭제 + 취소
들어간 파일 0개면 `폴더를 압축하는데 오류가 발생했습니다.`
```

- 원본은 bit7z(7-Zip) 로 압축하고 암호를 걸지 않는다. Go 는 `archive/zip`(표준 라이브러리) 으로 충분하다.
- **이름 인코딩**: Go `archive/zip` 은 이름이 UTF-8 이고 ASCII 가 아니면 범용 비트 11(UTF-8 표시)을 켠다. bit7z(7-Zip) 의 기본도 비 ASCII 이름에 UTF-8 표시를 쓰는 것으로 추정한다. 받는 쪽(원본 snbApp 의 `ExtractEach`, MOSFM, 7-Zip, Windows 탐색기)에서 한글 폴더·파일 이름이 깨지지 않는지 9절에서 확인한다.
- 큰 폴더 압축은 시간이 걸리므로 진행을 서랍 행에 `압축 중 N%`(바이트 기준)로 보인다(원본은 압축 중 표시 없음, 8절).
- 압축은 Deflate 기본 수준. 이미 압축된 파일(jpg·zip·mp4)이 많으면 `zip.Store` 가 빠르지만 판단 비용이 들어 하지 않는다(YAGNI).

### 7.10 자동 업로드

```
망마다 time.Ticker(period 분). 켜짐·폴더 있음일 때만.
주기마다:
  problem := folderProblem(folder)  // 빈 값, 없음, 폴더 아님, 읽기(os.ReadDir) 실패, 쓰기(os.CreateTemp ".snb_write_*" 만들고 지움) 실패
  if problem → 로그만
  done := folder/done 없으면 MkdirAll 하고 이번 주기 끝(실패면 창)
  목록 := os.ReadDir(folder) 중 숨김·done 제외(하위로 내려가지 않음)
  uploadFiles(server, 목록, isAuto=true)
성공 이벤트 → 행 경로의 부모 == folder 이면 os.Rename(→ done/이름, 겹치면 번호)
```

- 원본의 NTFS 권한 검사(읽기 가능)는 `os.ReadDir` 실패로 대신한다(실제로 읽어 보는 것이 가장 정확).
- 원본은 주기마다 폴링이다. fsnotify 는 쓰지 않는다(원본 동작과 같고 의존성 하나를 덜 쓴다).

### 7.11 진행률 이벤트

- 워커는 바이트를 atomic 으로만 올린다. Go 쪽 타이머 하나가 200ms 마다 바뀐 행만 모아 Wails 이벤트 `transfer:progress` 한 번으로 보낸다(행마다·청크마다 보내지 않는다 ― 원본은 청크마다 신호).
- 상태 바뀜(대기→진행→완료/실패/취소)은 즉시 `transfer:state` 이벤트.
- 서랍의 전체 진행률·요약은 Svelte 쪽에서 store 로 계산.
