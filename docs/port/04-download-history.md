- [파일전송] 화면의 **서버파일 목록**: 조회·새로고침·자동 재조회, 칸 12개, 상태 글자와 색, 선택 칸·전체선택, 우클릭 메뉴, 빈 상태

- **전송내역·결재내역** 화면: 기간 조회, 단어 거르기, 정렬, 엑셀 저장

## 3. 서버 통신

모든 단건 RPC 에는 원본과 같이 **15초 상한**(`rpcTimeout`)을 걸고, 메타데이터 `auth-token` 에 사전로그인 토큰을 싣는다(Wails 판
`Session.ctx` 그대로). 스트림(`FileDownload`)은 상한 없이 취소 가능한 컨텍스트로 연다. 원본의 "[3311]" 같은 번호는 옛 TCP
전문 번호이고 로그 문구에만 남아 있다.

### 3.1 서버파일 목록 ― `ServerFileService.GetServerFileList` [3310]/[3311]

### 3.3 받기 ― `ServerFileService.FileDownload`(서버 스트림)

요청 `FileDownloadRequest`: 파일은 `spath = server_str`, `fpath` 는 비운다(`FileTransfer.cpp:1631`). 클립보드는 07 영역(`fpath="__CLIP__"`).

응답 스트림 `FileDownloadResponse`(oneof): `chunk`(파일 바이트) 여러 개 뒤에 **마지막에** `answer` 하나
(서버 `svc_filedownload.go:154-170`):

| `answer` 필드 | 값 |
|---|---|
| `res` | 1 |
| `code` | 3 |
| `reason` | 검사값(SHA-256 16진). 서버는 사용자 프로파일 `fm_checksum` > 0 이고 DB 에 검사값 칸이 있을 때만 채우고, 아니면 빈 값(서버 `:113-124`) |
| `length` | 보낸 바이트 수 |

받기 판정 순서(원본 `FileTransfer.cpp:1660-1985`, Wails 판 `client.go:394-453` 이 대부분 같다):

1. `answer.res != 1` 이면 실패: `code` 로 문구(5.6)를 골라 `파일 송수신 실패` 창. 쓰던 임시 파일만 지운다.
2. `answer` 의 검사값 채택: `code == 3 && reason != ""` 일 때만(`ChecksumVerdict.cpp:57-64`). 옛 서버(2026-03-05 이전)는
   `code 0` 에 `Successfully downloaded file` 을 싣는데 이것은 검사값이 아니다.
3. 스트림 종료 뒤 **받은 바이트 ≠ 목록의 `file_size`** 면 받은 것을 지우고 `DOWNLOAD_SIZE_MISMATCH` 문구. 서버 원본이 비었거나
   도중에 끊겨도 스트림은 정상 종료하기 때문이다.
4. 검사값이 있으면 받은 파일의 SHA-256(소문자 16진)과 비교. 다르면 지우고 `-45` 문구. **원본은 대소문자를 가려 비교한다**
   (`FileTransfer.cpp:1797`) ― Wails 판의 `strings.EqualFold` 를 유지한다(원본 확인 필요 4 를 피함). 16진이 아닌 서버값도
   비교해 불일치로 막는다.
5. 덮어쓰기면 원래 파일을 지우고 `.snbpart` 를 원래 이름으로. 이름을 못 바꾸면 번호 붙인 이름으로 남기고 경고, 그것도 못 하면
   `파일 열기 실패`(5.6).
6. 폴더면 zip 을 풀어 옮긴다(7.6). 실패하면 받기 실패이고 아래 7 로 가지 않는다.
7. 성공 처리: 전송 상태 100%·`완료`, 결재 다운로드가 아니면 `max_downlod_count` 가 **있고 1** 일 때만 `RemoveFile(spath, flag 1)`.

**지금 Go 서버의 거절은 `answer` 가 아니라 gRPC 오류 상태다**(서버 `svc_filedownload.go:88-110`, `return fmt.Errorf(...)`):

| 서버 오류 메시지 | 뜻 | Wails 판 화면 문구(원본 코드 문구에 대응) |
|---|---|---|
| `invalid Downloadfile name format` | 서버 경로 형식 오류 | `서버에서 파일 데이터를 받지 못했습니다.` |
| `not allowed to download file to Inner PC` | 업무망 받기 권한 없음 | `업무망 파일 다운로드 권한이 없습니다.`(원본 -31) |
| `not allowed to download file to Internet PC` | 인터넷망 받기 권한 없음 | `인터넷망 파일 다운로드 권한이 없습니다.`(원본 -33) |
| `file size exceeds limit` | 크기 상한 초과 | `파일사이즈가 전송사이즈(%1)를 초과하였습니다.`(원본 -32/-34, `%1` 은 로그인 응답의 파일 크기 상한을 사람이 읽는 단위로) |

원본 클라이언트는 이 오류 상태를 보지 않고 3번(크기 불일치)으로 떨어져 `받은 크기(0 바이트)가 서버 파일 크기(N 바이트)와 달라
저장하지 않았습니다.` 를 보인다(코드 판독: `FileTransfer.cpp:1748-1784` 의 `finished` 처리기가 `status` 를 로그에만 쓴다. 실행 확인은
안 함). Wails 판은 위 표로 원인을 그대로 알린다. 모르는 메시지는 `전송 실패` + 원문을 로그에.

### 3.4 서버 파일 삭제 ― `ServerFileService.RemoveFile` [3036]

`imports/FileMoverGrpc/FileTransfer.cpp:2470-2519`, `src/ViewController.cpp:1187-1211`.

## 6. 경계·오류 상황

원본이 처리하는 것(○), 원본의 결함 의심이라 Wails 판에서 다르게 할 것(△).

1. ○ 받을 수 있는 것과 없는 것을 섞으면 폴더 창은 뜨고, 없는 것은 폴더를 고른 뒤 안내와 함께 빠진다. 하나도 없으면 폴더 창이 안 뜬다.
2. ○ 확인 창이 떠 있는 동안 온 수동 받기·결재 받기는 미뤄졌다가 창이 닫힌 뒤 순서대로 처리된다. 미룬 요청은 처리할 때의 체크를 다시 읽고 폴더만 요청 때 값이다.
3. ○ 결재 받기 겹침 거절(`받는 중`)은 미루기보다 먼저 걸린다(06 영역).
4. ○ 같은 이름 판정은 저장할 때와 같은 이름 정리(Windows 금지 글자 → 공백) 뒤에 비교한다. 정리 전 이름으로 비교하면 묻지 않고 지나친다.
5. △ 폴더 이름은 `fileName.replace(".zip","")` 라 이름 중간의 `.zip` 도 지운다(`src/ViewControllerUiSlot.cpp:72-74`) → 끝의 `.zip` 만 뗀다(`strings.TrimSuffix`, 대소문자 무시 권장).
6. ○ 번호는 `_00000`~`_99999`. 다 차면 원본은 원래 이름에 덮어쓴다(`filemoverutil.cpp:43-50`) → Wails 판은 실패(`파일 열기 실패`)로 끝내는 편이 안전하다.
7. △ 검사값 대조가 대소문자를 가린다(원본) → 무시한다(Wails 판 현행 유지).
8. ○ 디스크 여유: 수동 받기는 "이 사용자가 쓸 수 있는 바이트"(`QStorageInfo::bytesAvailable`)로 본다. 자동 받기는 `bytesFree` 이고 `freeSize <= 0` 은 부호 없는 값이라 0 일 때만 걸린다 → Wails 판은 둘 다 "쓸 수 있는 바이트" 하나로.
9. ○ 받기 실패 창은 로그인 상태일 때만 뜬다.
10. △ 자동 다운로드 예약은 켜짐을 예약할 때만 본다. 켜고 30초(또는 목록 뒤 10초) 안에 끄거나 로그아웃해도 한 번 돈다(DN-060) → 실행 때 세션·설정을 다시 본다.
11. △ 서버파일 모델이 앱에 하나라 여러 망의 응답이 서로 덮는다(현재 망 필터가 주석) → 망(세션)마다 목록을 따로 든다. 09 영역과 함께.
12. ○ 끌기 감지 파일이 사용자 데이터 폴더 안에 생기면 무시한다(끌기 원본이 거기 있다).
13. △ 서버 알림 종류 `MSG_KIND_FILE_LIST` 처리에 `break` 가 없어 결재 목록 갱신까지 이어진다(`FileMoverGrpc.cpp:2574-2580`, 09 영역).
14. △ 서버 거절(`res`≠1)이나 응답 없이 끝날 때 덮어쓰기가 아닌 새 파일은 닫기만 하고 지우지 않는다(DN-047, 코드 판독). 단 지금 Go 서버의 거절은 gRPC 오류라 크기 불일치 갈래에서 지워진다. Wails 판은 늘 `.snbpart` 라 해당 없음.
15. ○ 받은 크기 0 이고 서버 크기도 0 인 파일: 크기 대조는 통과한다. 진행률 계산에서 0 으로 나누지 않는다(`FileTransfer.cpp:1753-1756`).
16. ○ 서버 원본이 비었거나 스트림이 도중에 끊겨도 스트림은 정상 종료한다 → 크기 대조로 막는다.
17. ○ 덮어쓰기 대상을 다른 프로그램이 잡고 있으면 교체 실패 → 번호 붙인 이름으로 남기고 경고 로그. 그것도 실패하면 `파일 열기 실패`.
18. ○ 폴더 받기: 압축 안 경로가 풀 폴더 밖이거나 링크면 아무것도 풀지 않는다. 상한(10GiB·10만 개·여유 1GiB)에 걸리면 목적 폴더를 건드리지 않는다. 풀기에 실패하면 받기 실패이고 서버 원본도 지우지 않는다.
19. ○ 폴더 [이름 변경]은 새 번호 폴더에, [덮어쓰기]는 기존 폴더에 병합(같은 이름 파일만 바뀌고 나머지는 남는다). 새 폴더였는데 옮기다 실패하면 지운다.
20. ○ 같은 요청 안의 이름 같은 두 행: 앞 것만 묻고 뒤 것은 말없이 번호.
21. ○ 물은 뒤 받기 직전에 같은 이름이 새로 생기면(다른 받기가 먼저 끝남) 말없이 번호.
22. ○ 클립보드 행(`__CLIP__`)은 [파일 다운로드] 대상이 아니다(클립보드 다운로드는 07).
23. ○ 사후승인 완료(`state`=3)는 `다운로드 가능`(코드 1)이다. **Wails 판 현행 `downloadBlock` 은 이것을 막는다 → 고친다.**
24. ○ 모르는 `virus_flag`·`priv_state`·`state` 값은 `다운로드 불가`(코드 -1)로 막는다.
25. △ 동일망 행은 코드 -1 이라 원본 칩 색 규칙의 "동일망 = 경고색"(aprvState 5) 갈래에 닿지 않고 회색이 된다(`settings/FileStatus.qml:56` vs `ViewControllerUiSlot.cpp:87`) → Wails 판은 상태 종류를 따로 들어(7.1) 경고색을 준다.
26. ○ 자동 다운로드: 같은 파일이 전송 상태 표에서 아직 진행 중이면 다시 넣지 않는다. △ 원본은 PC 이름(`fileName`)으로 비교해 이름이 같은 다른 서버 파일도 건너뛴다 → `server_str` 로 비교.
27. △ 자동 다운로드 + `max_downlod_count` 가 1 이 아닌 서버: 받은 파일이 목록에 남아 목록이 바뀔 때마다 다시 받을 수 있다(원본 확인 필요 5, 확인 안 됨) → Wails 판은 "이번 로그인에서 자동으로 받은 `server_str`" 집합을 들어 다시 받지 않는다.
28. ○ 자동 다운로드 중 서버 경로·인쇄 폴더를 못 만들면 `정보` 창 `자동다운로드폴더 생성에 실패했습니다. -<경로>`.
29. ○ 자동 다운로드는 사용자 폴더가 없거나 쓸 수 없으면 한 건도 받지 않고 로그만(`자동다운로드 >>> 사용자 폴더로는 받지 않는다(autoDownloadFolder_<n>): <까닭>`).

### 7.6 폴더(zip) 풀기 ― `FileTransfer.cpp:1895-1941`, `imports/ZipExtractor`

원본은 bit7z(7-Zip DLL). 폴더 업로드는 업로더 앱이 Deflate zip 으로 묶는다(`zipextractor.cpp:152-155`, 비밀번호 없음 ― 폴더 받기의
`ExtractEach(..., "")`). Go 표준 `archive/zip` 으로 풀 수 있다(Store·Deflate). 알고리즘:

1. 임시 zip 을 받는다(크기·검사값 대조는 zip 바이트로).
2. 작업 폴더 `os.MkdirTemp(<사용자 데이터>/temp, "x")` 를 만든다.
3. `zip.OpenReader` 로 항목마다:
   - 이름의 `\` 를 `/` 로 바꾼 뒤 `filepath.IsLocal`(Go 1.20+)이 거짓이면(절대 경로·`..`·드라이브 문자) **전체 중단** → `FOLDER_UNZIP_UNSAFE`.
   - 심볼릭 링크(`Mode()&fs.ModeSymlink`)면 전체 중단 → 같은 코드.
   - 항목 수 > 100000 → `FOLDER_UNZIP_LIMIT_ITEMS`(문구 인자 `100000`).
   - 실제로 쓴 바이트 누계가 10GiB 를 넘으면(헤더의 `UncompressedSize64` 를 믿지 말고 `io.CopyN` 으로 상한 +1 까지 세어) → `FOLDER_UNZIP_LIMIT_SIZE`(인자 = 10GiB 를 7.2 형식으로).
   - 풀기 전·중에 디스크 여유가 (남은 예상량 + 1GiB) 아래로 떨어지면 → `FOLDER_UNZIP_DISK_SPACE`.
   - 그 밖 오류 → `FOLDER_UNZIP_FAILED`.
   전부 검사하고 나서 쓰기를 시작하는 원본 방식(경로 이탈이면 아무것도 풀지 않음)을 따른다: 1회차로 목록 검사, 2회차로 쓰기.
4. 다 풀리면 작업 폴더의 내용을 목적 폴더로 옮긴다(병합: 같은 상대 경로의 파일은 바꾸고 나머지는 둔다). 같은 디스크면 `os.Rename`,
   다르면 복사 후 삭제. 목적 폴더가 새것이었는데 옮기다 실패하면 목적 폴더를 지운다.
5. 작업 폴더·임시 zip 삭제(`defer os.RemoveAll`).

주의: 다른 클라이언트(MOSFM 등)가 만든 zip 의 항목 이름이 UTF-8 플래그 없이 CP949 일 수 있다. 추정: 그때는
`golang.org/x/text/encoding/korean.EUCKR` 로 바꿔야 이름이 깨지지 않는다(원본 bit7z 는 7-Zip 이 OEM 코드 페이지로 읽는다).
`zip.File.NonUTF8` 가 참이고 UTF-8 로 유효하지 않으면 CP949 로 풀어 본다.

  [결재자]·[결재일시]·[결재사유]의 `-` 는 그대로 쓴다.
- 칸 폭 = 그 칸의 가장 긴 글자 수 × 1.2.
- 파일 쓰기는 작업 스레드, 앞 저장이 도는 중이면 거절. 로그 `[내역] 엑셀 저장: <경로> N 건 Mms`.
- Go: `github.com/xuri/excelize/v2` ― `MergeCell`, `NewStyle`, `SetCellStr`(글자 셀, `SetCellValue` 는 쓰지 않는다), `SetCellInt`, `SetColWidth`.
  CSV 를 추가로 둘 때(원본 WASM 규칙, `TransHistoryModel.cpp:345-361`): UTF-8 BOM, `= + - @` 등으로 시작하는 칸은 앞에 `'`, 쉼표·따옴표·줄바꿈이
  있으면 따옴표로 감싸고 `"` 를 `""` 로.

### 7.10 끌어서 받기(원본 방식과 Wails 판 대안)

원본(DN-050·051): 끌기 시작 때 `<사용자 데이터>/__DragFilesDownloding__` 임시 파일을 `text/uri-list` 로 내보내고, 탐색기가 그것을
복사해 놓으면 `DriveWatcherThread` 가 Windows 의 모든 고정·네트워크 드라이브를 하위까지 감시하다 그 이름의 파일이 생긴 폴더를 받을
폴더로 삼는다(mac·Linux 는 `~/Downloads` 만). Wails v3 의 끌기 API 는 앱으로 **들어오는** 파일 드롭만 다룬다(추정: v3.0.0 문서·소스에
나가는 드래그 API 를 보지 못함). 드라이브 전체 감시는 비용과 오탐이 커서 옮기지 않는다. 대안: Windows 는 OLE `DoDragDrop` +
`CFSTR_FILEDESCRIPTORW`/`CFSTR_FILECONTENTS` 지연 렌더링(받는 쪽이 놓을 때 받기 시작)을 `golang.org/x/sys/windows` + `go-ole` 로 직접
구현 ― 난이도 상. 1차 판은 폴더 선택 창과 탐색기 패널(12 영역)로 충분하다.

### 7.11 검사값

SHA-256, 소문자 16진. Wails 판 `io.MultiWriter(out, sha256.New())` 로 받으면서 계산 ― 원본은 다 받은 뒤 파일을 다시 읽는다
(`FileTransfer.cpp:1792`). Wails 판 방식이 디스크 읽기 1회를 아낀다(유지).

## 8. 원본보다 낫게 할 수 있는 곳

### 성능

1. **받기 중 해시 동시 계산**(Wails 판 현행): 원본은 다 받은 뒤 파일 전체를 다시 읽는다 ― 1GB 에서 수 초.
2. **버퍼 쓰기**: `bufio.NewWriterSize(f, 1<<20)` 로 청크마다 쓰기 시스템 호출을 줄인다. 진행률 이벤트는 100ms 에 한 번으로 묶어 웹뷰로
   보낸다(Wails 이벤트가 청크마다 나가면 화면이 밀린다).
3. **목록 갱신 비용**: 원본은 목록이 바뀌면 모델을 통째로 비우고 다시 채운다. Wails 판은 Go 에서 변화 판정 뒤 바뀐 경우만 화면으로 보내고,
   Svelte 는 `server_str` 키로 `{#each}` 해 바뀐 행만 다시 그린다. 1만 행 이상이면 가상 스크롤(보이는 행만 DOM) ― 외부 라이브러리 없이
   고정 행 높이로 직접 짤 수 있다.
4. **내역**: 원본은 응답마다 표를 처음부터 다시 채우고 화면 스레드에서 한 행씩 넣는다(수만 건 측정 없음). Go 에서 다 모은 뒤 한 번에
   보내고, 정렬·거르기는 프런트에서 배열로(1만 건은 수 ms).
5. **삭제 병렬**: 원본처럼 동시 상한을 두되(예: 8) 고루틴 + `errgroup` 으로, 끝나면 목록 한 번 재조회.
6. **받기 병렬**: 대기열·동시 수는 03 영역과 공용. 다운로드도 업로드와 같은 동시 상한(원본 5)을 따른다.
7. **메모리**: 스트림 청크를 바로 파일에 쓰므로 파일 크기와 무관하게 일정. zip 풀기는 `io.CopyN` 스트리밍.
